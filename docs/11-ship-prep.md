```
Directly is Instagram with the scrolling removed.

It opens straight into your messages and takes away the feed, Reels and Explore. You keep the parts
you actually use — your conversations, your notifications, profiles you look up on purpose — and lose
the parts that swallow an hour.

WHAT YOU KEEP
• Your DM inbox, threads, notes and message requests
• Sending text, photos, voice notes, stickers and reactions
• A badge on the DMs tab and on the app icon when messages are waiting
• Notifications, including Follow Back
• Profiles you search for deliberately
• One reel or post a friend sends you, opened on its own

WHAT'S GONE
• The home feed
• The Reels tab, and the next reel after this one
• Explore, search grids and suggestions
• Stories, unless you turn them back on
• Any link in a conversation that points into the above

HOW IT WORKS
Directly shows you Instagram's own pages in a single, dark-themed view and hides the parts that lead
somewhere endless. When you open a reel a friend sent, it plays and loops; swiping up does nothing;
back returns you to the conversation. If something would take you to the feed, you land in your inbox
instead, with a short note explaining why.

WHAT IT DOES NOT DO
• It does not read, store or send your messages or your password
• It does not have an account system, analytics or a server
• It cannot alert you once the app is closed: a WebView cannot receive push notifications, and the
  only way to know about a message in the background would be a server holding your session — the
  thing this app exists not to have. You get the badge and a local alert while it is open.
• It does not automate anything: no auto-likes, no auto-follows, no automatic messages
• It does not modify your Instagram account in any way

Your session lives where Instagram put it — in this app's own web view or in your browser — exactly as
it would anywhere else. The app ships with a Safari extension so that instagram.com behaves the same
way in Safari.

Directly is an independent project. It is not affiliated with, endorsed by or sponsored by Instagram
or Meta. Instagram is a trademark of Meta Platforms, Inc.
```

## 3. App Privacy ("nutrition label")

Answer: **Data Not Collected.** Every category — contact info, identifiers, usage, diagnostics,
purchases, location, contacts, user content — is "not collected", because there is no server and no
analytics SDK. Nothing is linked to the user; nothing is used for tracking.

The one nuance to declare honestly if a reviewer asks: the app stores settings on the device. That is
not "collection" under Apple's definition (not transmitted off-device).

### Sideloading the unsigned IPA

The IPA attached to `latest` is built with `CODE_SIGNING_ALLOWED=NO`, so iOS refuses it until it
carries a signature from a team the device trusts — the download is for handing to a signer, not for
AirDropping to a phone. Three routes, easiest first.

1. **Sideloadly or AltStore.** Install the tool on a Mac or PC, connect the phone, drag
   `directly-main-unsigned.ipa` in, enter your Apple ID, choose your team, press Start. Both re-sign
   with your own free profile. A free account's profile expires after 7 days and the app then refuses
   to launch until it is signed again; AltStore can refresh it on a schedule, Sideloadly cannot.

2. **Let Expo sign it.** This is the route the rest of this repo assumes, because it needs no IPA:

   ```bash
   cd apps/ios
   npx expo prebuild --platform ios --no-install
   npx expo run:ios --device          # signs with the team in your Xcode account, installs over USB
   ```

   For a file to give to someone else, `eas build --platform ios --profile preview` builds an
   internal-distribution IPA with your Apple account and registers the device UDIDs through EAS
   (`eas device:create`). That is the only route here that produces an IPA which installs on a phone
   that is not plugged into your machine.

3. **Sign it yourself** — a paid team with a Development or Ad Hoc profile that already lists the
   device. `tools/resign-ipa.sh` is that, in one command:

   ```bash
   tools/resign-ipa.sh ~/Downloads/directly-main-unsigned.ipa \
     --profile ~/Downloads/Directly.mobileprovision \
     --device 00008110-000A1B2C3D4E5F60     # checks the UDID, then installs with devicectl
   ```

   It embeds the profile, takes the entitlements from the profile rather than a guess, signs nested
   code deepest-first (a framework inside a framework before its container), verifies each nested
   item and then the bundle, and writes `…-signed.ipa` beside the input. It also takes a local `.app`
   instead of an IPA — the archive that Xcode leaves in `build/Build/Products/Release-iphoneos` when
   built with `CODE_SIGNING_ALLOWED=NO` — so a build from this machine can be signed without going
   through the release. `--dry-run` prints the plan and signs nothing; `--identity` overrides the
   first codesigning identity in your keychain; `--keep` leaves the signed `.app` behind for
   `ios-deploy` or Xcode.

   Three failures worth recognising, all caught before the phone is involved: *"not signed with a
   valid certificate"* means a nested binary kept its old signature; an app that opens then dies on
   launch means the profile's UDID list does not include that phone, which re-signing cannot fix; and
   the same open-then-die with the profile's UDID present means the profile's App ID does not match
   `com.directly.app`. The script compares the bundle id against the profile's `application-identifier`
   and refuses an expired profile, so neither of the last two gets as far as an install.

## 9. Rolling `latest` release

`.github/workflows/release.yml` builds on a tag push and on manual dispatch. A dispatch
ignores the ref name and publishes the rolling prerelease `latest` with both artifacts,
`directly-main.apk` and `directly-main-unsigned.ipa`:

```bash
gh workflow run release.yml --ref main   # build, then publish `latest`
gh run watch                             # APK ~12 min, then iOS, then publish
gh release view latest --json tagName,targetCommitish,assets
```

The publish job carries one non-obvious step, and it exists because of a GitHub
behaviour: an existing release is never re-pointed. `gh release create --target` runs only
when the release does not exist yet, and `gh release upload --clobber` replaces the files
without moving the tag. A rolling release therefore drifts — `latest` sat on `b04dafc`
while its downloads were built from a later commit, so the tag named code that was not in
the binaries. The job now moves the ref and the metadata itself:

```bash
git tag -f latest "$GITHUB_SHA"
git push --force origin refs/tags/latest
gh api -X PATCH "repos/$GITHUB_REPOSITORY/releases/$release_id" \
  -f target_commitish="$GITHUB_SHA"
```

The force-push is only ever `latest`, never a version tag, and the metadata patch is
allowed to fail: the files are already uploaded by that point, so a metadata hiccup must
not fail a release. After a dispatch, the tag, `targetCommitish` and both assets should
all name the same commit. If the tag moved and the files did not, the run died before the
upload.

### Release notes

The body of a versioned release is `docs/releases/<tag>.md`, so the text a version was
announced with is reviewable in the same tree as the code it describes. Write the file
before pushing the tag:

```bash
$EDITOR docs/releases/v0.2.0.md
```

If the file is missing, the job falls back to one generated line naming the commit and
the signing state — that is what `latest` gets, since it is a different build every time.
The job also runs `gh release edit --notes-file` unconditionally: a release that already
exists keeps whatever body it was created with, so without that step `latest` would go on
describing a build it no longer carries.
